# AI 리터러시 웹앱 출시 전 정리 의사결정 질문지

- 작성일: 2026-08-31
- 작성자: 회색여우 코덱스
- 상태: 사용자 답변 대기
- 대상: 모듈 1~4 및 공용 UI의 출시 전 정리 항목 1~7

## 문서 목적

현재 앱은 교실 파일럿을 진행할 수 있는 수준까지 왔지만, 최종 정리 전에 문구·안내 방식·모바일 동작·이미지·명칭·배포 기준을 한 번에 합의할 필요가 있습니다. 이 문서는 수정에 들어가기 전에 필요한 결정을 모아 둔 질문지입니다.

각 항목에는 코덱스의 **권장 기본안**을 함께 적었습니다. 별도 의견이 없는 항목은 “추천대로”라고 답하면 됩니다.

## 0. 전체 사용 조건과 작업 범위

### 확인할 내용

1. 주 사용자는 **초등 고학년~중학생, AI 활용 경험이 적은 학생**으로 확정할까요?
2. 기본 사용 기기는 태블릿·크롬북·노트북이고, 스마트폰은 보조 환경으로 볼까요?
3. 공식적으로 지원할 최소 화면 너비를 어디까지로 정할까요?
4. 화면에 표시하는 예상 시간은 숙련자가 아닌 **처음 혼자 체험하는 학생의 실제 시간**을 기준으로 다시 확인할까요?
5. 이번 정리 범위에 1~7번뿐 아니라 발견되는 명백한 오탈자, 접근성, 모바일 레이아웃 문제도 포함할까요?
6. 구조가 크게 달라지는 수정은 바로 적용하지 않고 별도 계획서로 먼저 확인받을까요?
7. 코덱스가 로컬 수정·검증·커밋·검토 ZIP·인계서를 만들고, Antigravity가 GitHub에 푸시·배포하는 현재 역할을 유지할까요?

### 권장 기본안

- 초등 고학년~중학생 AI 초보자를 기준으로 합니다.
- 태블릿·크롬북·노트북을 기본으로 하고 스마트폰도 사용할 수 있게 합니다.
- 최소 화면 너비는 **360px**로 정합니다.
- 예상 시간은 학생이 처음 혼자 체험할 때를 기준으로 표시합니다.
- 1~7번과 함께 명백한 오탈자·접근성·레이아웃 문제까지 정리하되, 큰 구조 변경은 계획을 먼저 공유합니다.
- GitHub 푸시와 배포는 계속 Antigravity가 담당합니다.

## 1. 문장과 호칭 전수 교정

### 현재 확인된 문제

- `하늘이은`, `하늘이이`, `하늘이을`처럼 이름과 조사가 어색하게 결합되는 문장이 있습니다.
- 같은 기능을 가리키면서 `AI`, `AI 금쪽이`, `박사 금쪽이 AI`, `금쪽이`가 혼용됩니다.
- 일부 안내는 학생에게 말을 거는 문장과 시스템 설명 문장이 섞여 있습니다.

### 확인할 내용

1. 데이터의 이름 `하늘이`는 그대로 두고 문장을 `하늘이는`, `하늘이가`, `하늘이를`처럼 자연스럽게 직접 작성할까요?
2. 이번에 모듈 1만 고칠까요, 아니면 모듈 1~4의 학생 노출 문구를 전수 교정할까요?
3. 기본 문체를 다음처럼 통일해도 될까요?
   - 설명: `~해요`
   - 행동 안내: 실제 버튼 이름을 포함한 짧은 명령형
   - 결과: `~했어요`, `~을 확인했어요`
4. 캐릭터와 기술을 구분해 **캐릭터는 ‘금쪽이’**, 일반 기술·판단 과정은 **‘AI’**라고 부를까요?
5. 조사 자동 처리 유틸리티를 새로 만들기보다 현재 고정된 이름에 맞춰 자연스러운 문장을 직접 쓰는 것으로 충분할까요?

### 권장 기본안

- 이름은 `하늘이`로 유지하고 문장을 직접 자연스럽게 고칩니다.
- 모듈 1~4의 학생 노출 문구를 모두 전수 교정합니다.
- 캐릭터는 `금쪽이`, 기술과 시스템은 `AI`로 구분합니다.
- 현재는 조사 처리 유틸리티를 추가하지 않습니다.

## 2. 행동 가이드와 실제 버튼의 일치

### 현재 확인된 문제

- 아직 `AI에게 알려주기`를 해야 하는데 가이드가 먼저 `다음 이야기`를 안내하는 경우가 있습니다.
- 아직 카드가 열리지 않았는데 두 장을 고르라고 안내하는 경우가 있습니다.
- `강조된 버튼을 눌러 보세요`처럼 어느 버튼인지 바로 알기 어려운 공통 문구가 있습니다.

### 확인할 내용

1. 모든 가이드는 **지금 당장 해야 할 행동 하나만** 안내하도록 할까요?
2. `강조된 버튼` 같은 표현을 없애고 `AI에게 알려주기`, `A 선택`, `다음 이야기`처럼 화면에 보이는 버튼 이름을 그대로 쓸까요?
3. A/B 선택 뒤에는 학습 설명을 토스트에 길게 쓰지 않고, `결과를 읽고 ‘다음’ 누르기`만 안내할까요?
4. 학생이 아쉬운 선택을 했을 때 `틀렸어요`라고 판정하기보다 선택의 결과를 보여주고 다시 생각할 기회를 줄까요?
5. 버튼이 아직 비활성 상태라면, 그 버튼을 누르라고 하지 않고 먼저 해야 하는 조건을 안내할까요?
6. 가이드가 언급한 버튼이 실제 화면에 있고 활성화되어 있는지 자동 테스트에 포함할까요?

### 권장 기본안

- 다음 행동 하나만 안내합니다.
- 실제 버튼 이름을 정확히 사용합니다.
- 학습 피드백은 결과 카드에 두고 가이드는 조작 안내에 집중합니다.
- 오답 판정 대신 선택의 영향과 재고 기회를 보여줍니다.
- 가이드와 버튼 상태의 일치를 테스트합니다.

## 3. 모바일 화면 전환과 스크롤 위치

### 현재 확인된 문제

- 모바일에서 모듈 1·2의 활동을 선택하면 이전 스크롤 위치가 남아 새 화면의 로드맵과 제목이 위로 사라질 수 있습니다.
- 모듈 3·4는 화면 전환 래퍼를 사용해 상대적으로 안정적입니다.

### 확인할 내용

1. 활동을 처음 열 때 어디로 이동할까요?
   - 페이지 맨 위
   - 헤더 아래 로드맵 시작점
   - 새 콘텐츠 제목
2. 큰 단계가 바뀔 때는 새 콘텐츠 제목이 보이면서 로드맵 끝부분도 살짝 보이도록 맞출까요?
3. 한 단계 안에서 `다음`으로 페이지를 넘길 때는 현재 활동 카드 상단으로 이동할까요?
4. `이전`을 눌렀을 때도 이전 콘텐츠의 시작점으로 이동할까요?
5. 활동 시작은 즉시 이동하고, 내부 페이지 넘김은 부드러운 스크롤을 사용할까요?
6. 운영체제에서 동작 줄이기를 켠 사용자는 애니메이션 없이 즉시 이동하도록 할까요?
7. 공간을 아끼기 위해 로드맵은 화면 상단에 고정하지 않는 방향이 맞을까요?

### 권장 기본안

- 활동 시작 시 **헤더 아래 로드맵 시작점**으로 즉시 이동합니다.
- 큰 단계 전환 시 새 콘텐츠 제목과 로드맵의 위치 관계를 유지합니다.
- 내부 앞·뒤 이동은 활동 카드 상단으로 부드럽게 이동합니다.
- `prefers-reduced-motion`을 존중합니다.
- 로드맵은 고정하지 않습니다.

## 4. ‘지금 해볼 일’ 안내 방식 통일

### 현재 확인된 문제

- 모듈 1은 하단 토스트만 사용합니다.
- 모듈 2는 상단 `이번 단계` 안내를 사용합니다.
- 모듈 3·4는 상단 안내와 하단 토스트가 동시에 나와 중복됩니다.
- 하단 토스트가 약 7초간 떠 있으면서 작은 화면에서 버튼이나 내용을 가릴 수 있습니다.

### 확인할 내용

1. 네 모듈 모두 **하단 `지금 해볼 일` 토스트 하나**로 통일할까요?
2. 모듈 2의 상단 `이번 단계`, 모듈 3·4의 상단 `지금 할 일`은 제거할까요?
3. 활동의 교육적 의미를 설명하는 `왜 할까요?`는 토스트의 작은 `?` 버튼에서 계속 볼 수 있게 할까요?
4. 더 중요한 학습 이유는 결과 카드와 요약 화면에서도 다시 확인하게 할까요?
5. 토스트는 현재처럼 7초 정도 유지할까요, 학생이 닫을 때까지 유지할까요?
6. 닫기 버튼을 누르면 현재 안내만 닫고, 다음 단계로 넘어가면 새 안내가 다시 나타나게 할까요?
7. 단순히 텍스트만 바뀌는 순간이 아니라 학생이 새 행동을 해야 할 때만 새 안내를 띄울까요?
8. 토스트가 떠 있는 동안 본문 하단에 안전 여백을 추가해 버튼을 가리지 않게 할까요?

### 권장 기본안

- 전 모듈을 하단 `지금 해볼 일` 하나로 통일합니다.
- 상단 중복 안내는 제거합니다.
- `왜 할까요?`는 `?`에 유지하고, 핵심 학습 의미는 결과 화면에서도 보여줍니다.
- 토스트는 7초 후 사라지되 직접 닫을 수도 있게 합니다.
- 다음 행동이 바뀔 때 새 안내가 나타납니다.
- 토스트 높이만큼 안전 여백을 확보합니다.

## 5. 이미지 용량과 프레임 정리

### 현재 확인된 문제

- 래스터 이미지 12개의 합계가 약 17.14MB이고, 1MB를 넘는 이미지가 6개입니다.
- 모바일 첫 진입에서 홈 썸네일이 잠시 비어 보일 수 있습니다.
- 이미지마다 여백과 크롭 방식이 달라 같은 카드 체계 안에서도 밀도가 달라 보입니다.

### 확인할 내용

1. 웹용 이미지를 WebP로 변환해도 될까요?
2. 원본은 어디에 보존할까요?
   - 외부 `금쪽이 리소스` 폴더
   - 프로젝트 `_history` 백업
   - 두 곳 모두
3. 실제 표시 크기에서 원본과 거의 구별되지 않는 품질을 목표로 할까요?
4. 홈 썸네일은 파일당 약 150~250KB, 캐릭터 이미지는 약 250~500KB를 목표로 해도 될까요?
5. 홈 첫 화면에서 내려받는 이미지 합계를 약 1.5MB 이하로 줄이는 것을 목표로 할까요?
6. 새 이미지를 생성하지 않고 현재 이미지의 크롭·프레임·여백만 통일할까요?
7. 첫 화면의 대표 이미지는 즉시 불러오고, 아래쪽·내부 활동 이미지는 지연 로딩할까요?
8. 원본 한글 파일명은 유지하고 웹용 사본은 영문 파일명으로 관리할까요?
9. 이미지 크기가 다시 커지는 것을 막기 위해 CI에서 파일 크기 제한을 검사할까요?

### 권장 기본안

- 원본은 외부 리소스 폴더와 `_history` 두 곳에 보존합니다.
- 웹용 사본만 WebP로 변환하고 영문 이름을 사용합니다.
- 실제 표시 크기에서 차이가 거의 없는 품질로 압축합니다.
- 홈 썸네일 150~250KB, 캐릭터 이미지 250~500KB, 홈 초기 이미지 합계 약 1.5MB를 목표로 합니다.
- 현재 이미지의 크롭·프레임·여백을 통일합니다.
- 첫 화면 이미지만 우선 로딩하고 나머지는 지연 로딩합니다.

## 6. 홈과 내부 프로그램 명칭 통일

### 현재 확인된 문제

- 홈에는 `공정한 AI 실험실`, `진실·미디어 검증소` 같은 기존 명칭이 남아 있습니다.
- 내부에는 `AI의 선택, 그대로 믿어도 될까?`, `진짜일까? 써도 될까?`처럼 학생이 이해하기 쉬운 제목이 사용됩니다.

### 제안 명칭

| 모듈 | 작은 분류명 | 학생용 제목 | 홈 설명 |
|---|---|---|---|
| 1 | 추천과 공정성 | AI의 선택, 그대로 믿어도 될까? | AI의 추천이 어떤 자료와 기준에서 나왔는지 직접 확인해요. |
| 2 | 정보와 미디어 확인 | 진짜일까? 써도 될까? | AI가 쓴 글과 미디어를 공개하기 전에 근거와 사용 조건을 확인해요. |
| 3 | 부탁과 역할 나누기 | AI에게 무엇을 맡길까? | AI에게 부탁하는 방법과 사람·AI가 나눠 맡을 일을 비교해요. |
| 4 | 확인·정지·복구 | AI가 대신 움직인다면? | AI가 행동하기 전에 확인하고, 이상 행동을 멈춘 뒤 복구해요. |

### 확인할 내용

1. 위 제목과 분류명을 홈과 내부 헤더에 동일하게 적용할까요?
2. 홈 카드에는 작은 분류명과 큰 학생용 제목을 함께 보여줄까요?
3. `공정한 AI 실험실`, `진실·미디어 검증소` 같은 이전 명칭은 학생 화면에서 없애고 기획 문서와 모듈 분류에만 남길까요?
4. URL과 폴더 이름(`/fairness`, `/verification`, `/role`, `/agent`)은 기술적 호환성을 위해 그대로 유지할까요?
5. 모듈 3·4의 제목도 위 제안처럼 질문형으로 맞추는 것이 좋을까요?

### 권장 기본안

- 제안 명칭과 설명을 홈과 내부 화면에 적용합니다.
- 작은 분류명 + 큰 질문형 제목 구조를 사용합니다.
- 이전 명칭은 학생 화면에서 제거하고 문서에만 보존합니다.
- URL과 소스 폴더 이름은 변경하지 않습니다.

## 7. GitHub 배포 전 자동 검증

### 현재 확인된 문제

- 현재 GitHub Pages 배포 과정은 의존성 설치 후 빌드만 실행합니다.
- 테스트나 린트가 실패해도 배포 전에 자동으로 막아 주는 단계가 없습니다.

### 확인할 내용

1. 배포 순서를 아래처럼 바꿀까요?
   1. `npm ci`
   2. `npm test -- --run`
   3. `npm run lint`
   4. `npm run build`
   5. 배포
2. `main` 푸시뿐 아니라 Pull Request에서도 같은 검증을 실행할까요?
3. 처음에는 별도 워크플로를 늘리지 않고 하나의 배포 워크플로 안에서 관리할까요?
4. 이미지 최적화 후 웹용 이미지 한 파일이 700KB를 넘거나 전체가 5MB를 넘으면 실패시키는 검사를 넣을까요?
5. 로컬에서는 `npm run check` 한 번으로 테스트·린트·빌드를 실행할 수 있게 할까요?
6. GitHub 로그에서 원인을 쉽게 찾도록 CI 단계는 테스트·린트·빌드로 분리해 표시할까요?
7. 검증 실패 시 새 배포를 중단하고 현재 정상 배포본을 그대로 유지하는 방식으로 할까요?
8. 코덱스가 로컬 변경과 인계까지만 하고 실제 푸시는 Antigravity가 맡는 원칙을 유지할까요?

### 권장 기본안

- `설치 → 테스트 → 린트 → 빌드 → 배포` 순서로 통과해야 배포되게 합니다.
- PR과 `main` 푸시 모두 검증합니다.
- 처음에는 한 워크플로에서 관리합니다.
- 이미지 최적화 뒤 적절한 용량 제한을 확정해 자동 검사합니다.
- 로컬용 `npm run check`를 추가하되 CI 로그는 단계별로 분리합니다.
- 실패 시 이전 정상 배포본을 유지합니다.
- GitHub 푸시는 Antigravity가 담당합니다.

## 추가 의사결정 A. 모듈 2 활동량

### 현재 판단

학교신문 검증 활동은 한 주장마다 여러 자료를 읽고 비교해야 하므로, 처음 사용하는 학생이 세 주장을 모두 처리하기에는 표시된 약 10분보다 길어질 가능성이 큽니다.

### 확인할 내용

1. 세 주장 모두를 필수로 유지할까요?
2. 기본 활동은 한 주장만 완료하고 나머지는 `다른 것도 해볼까요?`로 선택하게 할까요?
3. 기본·심화 모드를 구분할까요?
4. 예상 시간을 실제 체험 시간에 맞춰 늘릴까요?

### 권장 기본안

- **기본 활동은 한 주장 필수**, 완료 후 나머지 두 주장을 선택 활동으로 제공합니다.
- 심화 활동에서는 세 주장을 모두 검증할 수 있게 합니다.
